How to Use the Feedback System

A plain-English walkthrough — for the Admin, for Faculty, and for Leaders (HOD / Vice Dean / Dean).

Start here — what this is and how to open it

This system collects student feedback for every course, turns it into a report for each teacher, and — when a course scores poorly — asks that teacher to file a short Action Taken Report (ATR) which their HOD reviews. Three kinds of people use it:

WhoWhat they doHow they reach it
ADMIN Runs the whole thing: uploads data, opens the feedback window, sends links, downloads reports. On the laptop running the app, open http://localhost:5000/
FACULTY Teaching staff. Receive their result; if asked, file an ATR. No login — they use a private link emailed to them. Click the link in their email (works from any phone/PC on the college network)
LEADER HOD, Vice Dean, or Dean. Review the ATRs from their department and endorse or return them. Open http://<laptop-address>:5000/leader/login and sign in
The starting point is always the Admin. The app runs on one laptop on the college LAN. When the Admin starts it, everyone else connects to that laptop's address (for example http://192.168.1.7:5000). Nothing works until the Admin has it running.

Read left to right. Each box says who acts.

ADMIN  The Admin walkthrough

You run the app on the laptop and open http://localhost:5000/. You land on the Dashboard. Across the top is a menu — you'll work through it roughly left to right: Dashboard · Roster · Allocation · Enrollment · Offerings · Readiness · Categories · Templates · Cycles · Reports · Activity. Here is the whole flow.

  1. Create the cycle first. Everything else lives inside a cycle, so this is the very first thing you do. Click Cycles, then Create, and give it a code (like CA1) and a name. From now on you'll select this cycle on the pages below, and the roster and course allocation you load will go into it.
  2. Check the roster. Click Roster, make sure your new cycle is selected, and see the students loaded for it. You can upload the student list here (Upload) or edit a student. This is who will be asked for feedback. (For the exact columns of this and the other upload files, see Filling the upload files.)
  3. Load the course allocation. Click Allocation, choose the cycle, pick your allocation spreadsheet and upload it. Your sheet includes a feedback category column for every row (Theory, Lab, Skill, Ability Enhancement, or any category you've configured) — this is what decides which questionnaire each course uses. The system reads the file and shows a preview of the teaching assignments (which teacher takes which course). If any row has a missing or unrecognised category it is flagged here and not committed — fix it in the sheet and re-upload. When the preview is clean, click Confirm to commit.
  4. Add elective enrollments (if any). Click Enrollment, pick the elective course group and upload the list of students taking it. This tells the system which students should be asked about each elective. Skip this if you have no electives.
  5. Review the offerings. Click Offerings to see every course+teacher for the cycle. Each already carries the category you declared in the allocation sheet (it is required at upload, so nothing is ever left blank). If you need to change one, click Edit on that offering and pick a different category. The list of available categories is managed separately under Categories, where you can add new ones (for example INTERNSHIP) without any code change.
  6. Run the Readiness Check. Click Readiness. This is the safety gate: it looks for problems (missing categories, students with no courses, etc.) and shows READY or a list of things to fix. A real cycle cannot be opened until this says READY. (You may dismiss a specific warning with a reason if it's expected.)
  7. Set the invitation email. Back on Cycles, click Email next to your cycle to edit the message students will receive. The placeholders {student_name}, {cycle_name} and {link} are filled in automatically for each student, so each person gets their own private link.
  8. Open the cycle. Still on Cycles, click Open. The state changes to OPEN and the system is now ready to accept submissions. (If Readiness isn't READY, it will refuse and send you back to fix it.)
  9. Generate and send the links. Click Tokens for the cycle. Choose a batch — by programme, department and/or year — and click Generate. The system makes one private link per student. Tick Send email to email each student their own link.
    Email modes: if no email is set up, every message is instead saved as a file in the app's outbox folder (nothing actually sends) — perfect for a dry run. To really send, set up email first (see EMAIL-GMAIL-API-SETUP.md). A test cycle always redirects mail to one safe test address, so it can never message real students.
  10. Watch participation and nudge stragglers. Click Participation for the cycle to see, live, who has submitted and who is still pending. Click Send reminder to re-send links to those who haven't finished. You see who participated — never what anyone answered.
  11. Close the cycle. When collection is done, go back to Cycles and click Close. Submissions stop.
  12. Send results to teachers — and start the ATR workflow. This is the main post-close step. On Cycles, click Results & send for the cycle. That page walks you through four things, top to bottom:
    1. Set the POOR level. Type the pass mark out of 10 (for example 8 or 8.5). Optionally add an "any section below X" cut, and the minimum number of responses a course needs before it's judged. Click Save & re-classify.
    2. Run scoring & classification. One click scores every course and marks each GOOD or POOR against your level. Safe to re-run any time.
    3. Review the list. Every teacher's courses appear with the response count, overall score and band — below-mark courses highlighted in red — plus a count of how many teachers will be asked for an ATR.
    4. Edit the email and send. Adjust the short preamble, then click Generate & Send. Every teacher gets one email with a single combined PDF of all their courses; any course below the mark carries a "File your ATR" link in that same email. (Tick the box to also send HOD/Dean roll-up summaries.) To test first, type your own address in “Send everything to this address instead” — every email, for every teacher, comes to you.
    Just like the student links, browse the app at your laptop's LAN address (not localhost) before sending, so the ATR links work for teachers. In dev mode nothing is sent — each email, with its PDF attachments, is written to app/outbox/ so you can open and check it first.
    This is the bridge to the Faculty step below: sending is what puts the "File your ATR" link in a below-mark teacher's inbox and makes the ATR show up on their HOD's dashboard.
  13. (Optional) Download reports by hand. The send above already attaches each teacher's reports. If you also want copies for records, click Reports, pick the cycle, and download any single course as Excel or PDF, or a whole programme/year at once (a zip of Excel files or one combined PDF).
  14. Keep an eye on the log. Click Activity any time to see everything that has happened on the system — who did what, when, and from which device — with a quick summary at the top. Student submissions are never shown here (that protects anonymity).
Backup is simple: copy the app/data folder any time. The student roster lives in the permanent master.db; each cycle's answers live in their own file, so a cycle can be archived and reset without ever touching the master list.

ADMIN  Filling the upload files

Three spreadsheets feed the system: the student roster, the course allocation, and (only for electives) the enrollment list. On each upload page there is a Download template button — always start from that, so the column headings are already correct. Every upload runs as a dry run first: you see a preview, any bad row is flagged and not committed, and nothing is saved until you click Confirm.

Order matters: create the cycle, then upload the roster first, then the allocation. The allocation checks each course's class against the roster, so the roster has to be in place before it.

1 · Student roster

You do not list students one by one. Each row describes one group (a programme + year + section) as a range of register numbers, and the system expands that range into individual students automatically. Names aren't needed — each student's email is built as <register-no>@sriher.edu.in.

ColumnRequired?What to put
programme_codeYesThe E-code, e.g. E02
year_of_studyYes1 to 4
sectionYesA, B … or NA if the class isn't divided
reg_no_startYesFirst register number in the range
reg_no_endYesLast register number in the range
expected_countOptionalHow many students you expect in this range — used only as a cross-check (see below)

Optional: add a second sheet whose name starts with exclusion, holding a single column of register numbers to leave out (for example, detained students).

2 · Course allocation

One row per teaching assignment, kept flat — no merged cells. A course taught by three faculty is three rows; an elective basket with five options is five rows, each with its own teacher.

ColumnRequired?What to put

semesterYesODD or EVEN
programme_codeYesThe E-code, e.g. E02
year_of_studyYes1 to 4

Every programme_code + year_of_study + section on a CORE/LAB/PROJECT row must already exist in the uploaded roster, or that row is rejected in the preview. Electives are matched by the enrollment upload instead, not the roster.

3 · Enrollment (electives only)

Only needed for elective courses. One register number per row. The header register_no is optional. Every student listed must already be in this cycle's roster, and can't appear in another faculty's group for the same course.

About the “expected” counts (the double-check you asked about). expected_count (roster) and expected_students (allocation) are both optional. Their only job is a sanity check: when you run the Readiness check, the system counts how many students actually map to each course from the roster and compares it to the number you typed. If they differ by more than a small tolerance (more than 3, or more than 20%), it shows a soft warning like “found 38 vs expected 45.” It does not block you — it just flags a likely data slip (a missing roster row, a wrong section letter, a wrong year). Fill it in for your core / theory / lab courses where you know the strength; leave it blank for electives. If you leave it blank everywhere, nothing breaks — you simply lose that one automatic check.

ADMIN  Managing leader logins (Users & Roles)

Before any HOD, Vice Dean or Dean can review ATRs, they need a login. The system already created a placeholder account for every leader — one HOD per department, a Vice Dean and a Dean. Your job is simply to put the real names and emails on them and send each person a link to set their own password. It all happens on one page: Users & Roles in the top menu.

You never see or type anyone's password. You only send a one-time link; each leader chooses their own password privately.

Set up your leaders

  1. Open the page. Click Users & Roles in the top menu. You'll see every leader with their role, the department(s) they can see, whether they've set a password, and their last login.
  2. Personalise each leader. Click Edit on a row and replace the placeholder with the real person's name and institutional email (the email is their login username). Confirm the role and the department scope (see the table below), then click Save changes.
  3. Add anyone missing. If you need another leader, click + Add leader, fill in the same details, and save.
  4. Send the set-password invites. Use Send invite on one person's row, or Send invites to all without a password at the top to do everyone at once. Each leader gets an email with a one-time link (valid 7 days).
  5. Watch the progress. The Password column flips from Not set to Set once a leader has chosen theirs, and Last login shows when they were last in.
  6. Resend or reset. If a link expires, or a leader forgets their password, click Resend / reset on their row to email a fresh link.
  7. Remove access when needed. Click Disable to stop someone logging in (for example, when a leader changes role) without deleting their history; you can Enable them again anytime.

Email must be working for invites to actually send. The invites use the same emailer as the rest of the app. If Gmail sending is configured, they go out for real; if no email is set up, each invite is instead written to app/outbox/ as a .eml file (safe test mode) and the page tells you so. See EMAIL-GMAIL-API-SETUP.md to switch on real sending, and remember to restart / reload the app after changing the email settings.
If leaders will open their link from off campus, set FEEDBACK_PUBLIC_BASE_URL to your public address (e.g. your PythonAnywhere URL) so the emailed link is reachable. On the college LAN it just uses the address you're already using.

FACULTY  The Faculty walkthrough

If you teach a course, here is your whole experience. You never log in and you set no password. Everything reaches you by email, and every button is a private, one-time link.

  1. You get an email. After a feedback cycle closes, the Admin sends results. If one of your courses was rated POOR, your email includes a File ATR button (ATR = Action Taken Report — a short note on what you'll do to improve).
  2. Click the link. It opens a simple page showing your course and a text box. No login is asked — the link itself proves it's you, which is why you should not forward it.
  3. Write what you plan to do. In the box, describe the action you're taking (for example: "I will add weekly problem-solving sessions and share solved examples."). Then click Submit.
  4. It goes to your HOD. You'll see a "submitted" confirmation. Your ATR is now with your Head of Department for review. You're done — unless it comes back.
  5. If your HOD returns it. You'll get a new email with a reason and a fresh Revise link. Open it, update your note, and submit again. Repeat until it's endorsed.
If a link ever says it's invalid or expired, it has already been used or timed out. Ask the Admin to re-send you a fresh one.

LEADER  The Leaders walkthrough (HOD / Vice Dean / Dean)

Leaders review the ATRs from their own area and decide whether each is acceptable. You do log in (with a password you set yourself), and you only ever see your own department's ATRs — a HOD of one department can never see another's.

First time only — set your password

  1. Open the set-password email. The Admin sends you a one-time Set your password link. (The Admin never knows or holds your password.)
  2. Choose a password. The link opens a page with your email shown. Enter a password (at least 8 characters), type it again to confirm, and click Save. The link then stops working — it was one-time.

Every time — review ATRs

  1. Log in. Open http://<laptop-address>:5000/leader/login, enter your email and password, and click Log in.
  2. Open your dashboard. You land on the ATR dashboard. Pick the cycle from the dropdown. You see a list of the courses in your area and each ATR's status. Items waiting on you are marked as yours to act on.
  3. Review one ATR. Click Review on a row. You'll see the teacher's course and the action they wrote. Read it.
  4. Endorse or Return.
    • Click Endorse if the action is acceptable — the ATR is approved and moves on.
    • Click Return if it needs more — you must type a reason. The teacher automatically gets a fresh link to revise and resubmit.
  5. Chase missing ATRs. For a POOR course where the teacher hasn't filed yet, click Send reminder to email them their link again.
  6. Log out. Click Log out when you're finished, especially on a shared computer.
Vice Deans and the Dean work exactly the same way, but see a wider area — a Vice Dean sees their group of departments, and the Dean sees the whole college.

ADMIN  What's new in v2.1 — everything you need to run it

Version 2.1 adds a safe three-stage testing process, an admin login, a live status board, a one-click endorsement for the Dean/Vice-Dean, a signed audit record, and a clean way to turn a finished test run into the real thing. This section is the complete reference for all of it.

1 · The three testing levels (send safely, then go live)

Every cycle now runs at a testing level. You start safe and step it up as each level passes. The level controls who really gets email and whether reports are watermarked. Two test inboxes are configured in app/.env: the student test inbox (FEEDBACK_TEST_EMAIL, currently aishwarya.bramma@gmail.com) and the staff test inbox (FEEDBACK_FACULTY_ALIAS_EMAIL, currently aishwarya@sret.edu.in). Change either in .env.

A new cycle is born at Level 1. On the Cycles page each cycle shows a TEST L1/L2/L3 or PROD badge and a Set level dropdown to move it L1→L2→L3. You never set Production here — that happens only through Purge & promote (below).

The redirect is enforced in the mail code, not by addresses in a spreadsheet — so at Levels 1–2 a real student can never be emailed even if a cell was left un-edited.

2 · Purge & promote to production

When your Level-3 test passes, you do not create a new cycle. Instead, on the Cycles page click Purge → Production and type the exact phrase PURGE <CODE> (e.g. PURGE CA1) to confirm. This:

Wiped (gone)Kept (untouched)
All test feedback: student responses, tokens, ATRs and their trail, and the GOOD/POOR bands + marks derived from them. The Faculty Master, all course offerings, the student roster/enrollment, the templates, and this cycle's own settings (email text, thresholds).

The cycle flips to Production (Level 0) and back to DRAFT, ready for you to open and invite the real students. A timestamped backup of the purged data is saved in the app/archive/ folder first, so even this step is recoverable.

3 · Admin login (two accounts)

The admin console is now behind a login. There are two admin accounts — aishwarya@sret.edu.in and lekha@sret.edu.in — so actions are attributable to a named person (you'll see the logged-in email top-right, and it's recorded in the Activity log).

  • First password: go to /admin/login → Request a reset link (/admin/forgot), enter your email, and click the link that arrives.
  • Aishwarya is also the Vice-Dean: that login was kept as your Vice-Dean account and simply also granted admin access — you log in with your existing Vice-Dean password and you keep endorsing ATRs. (If you later hand the Vice-Dean role to someone else, admin access stays with you.)
  • Log out from the link at the far right of the admin menu.
Forgot your login? Three ways back in, safest first:
  1. Self-service: /admin/forgot emails you a reset link.
  2. No email available: on the server, run python admin_reset.py link aishwarya@sret.edu.in — it prints a set-password link to paste in a browser.
  3. Both locked out: on the server, run python admin_reset.py setpw lekha@sret.edu.in <newpassword> to set a password directly. (It only ever touches admin accounts, and needs server access, so it's a safe last resort.)

4 · Default banding: POOR below 7.5, minimum responses 0

By default a course is flagged POOR (an ATR is required) when its overall score is below 7.5 out of 10, and every scored course is banded (minimum responses = 0). You can still override both per cycle on the Results & send page before you classify.

5 · Archiving hides a finished cycle

When you Archive a cycle it disappears from every dropdown (dashboard, offerings, students, reports, uploads, the leaders' and HODs' views) — the whole point of archiving. It remains visible in one place only: the Cycles page, plus the Activity audit log.

6 · The Status board

The new Status menu shows, for one cycle: student participation (invited / completed / pending) and an ATR tracking table — which teachers were flagged POOR, who has and hasn't submitted their ATR, and which HOD / Vice-Dean / Dean hasn't acted yet. Filter by department, by exact ATR state, by "waiting on" (Faculty not submitted / HOD not acted / Vice-Dean / Dean / Closed), and by a free-text search over faculty and course.

7 · Endorse all (Dean & Vice-Dean) and "RECORDED"

On the leader ATR dashboard the Dean and the Vice-Dean get an Endorse all (N) button that endorses every ATR currently waiting on them in one click (the Vice-Dean's is limited to her departments). Each endorsement is still recorded individually in the audit trail. When the Dean endorses the last ATR, the whole cycle turns COMPLETE & RECORDED — your signal that it is ready for the audit report and archive.

8 · The signed audit report (for auditing)

Once a cycle is RECORDED, open the Cycles page and click Audit report. The system builds ONE consolidated PDF — students on roster vs who participated, every course's faculty with feedback count and mark out of 10, which teachers were given an ATR and their written explanation, and the full endorsement trail — then digitally seals it so any later change is detectable. A copy is also saved in app/archive/. Store the signed PDF in the Dean's or Vice-Dean's Drive as the audit reference.

Verifying the signature. Open the PDF in Adobe Reader. It shows the document is signed and unchanged, signed by "SRET Automated Feedback System". Because the certificate is the college's own (self-managed, not bought from a public authority), Adobe adds "signer's identity is unknown" until someone does a one-time Add to Trusted Certificates for it — the was-it-tampered proof is valid either way. Each report also prints a SHA-256 fingerprint as a second check.

Optional — a trusted timestamp. For a stronger audit record you can also embed an RFC-3161 trusted timestamp: an independent Timestamp Authority (TSA) cryptographically attests when the document was signed, so the date can't be disputed and the signature stays verifiable for years (long-term validation). To enable it, set FEEDBACK_TSA_URL in app/.env to a TSA endpoint (e.g. the free https://freetsa.org/tsr). When it's set and reachable, the report is signed and timestamped; when it's blank or unreachable the report still generates (signed, just without the timestamp) and says so. Caveat: PythonAnywhere's free tier blocks outbound TSA calls — this needs a paid tier or the TSA host whitelisted.

The full audit chain, end to end: generate PDF → embed SHA-256 fingerprint → digitally sign (institutional certificate) → add trusted timestamp (if a TSA is configured) → save a copy in app/archive/ → store the same signed PDF in the Dean's / Vice-Dean's Drive as the official audit reference.

8a · Recommended — sign on your laptop (no server whitelisting)

The signing and timestamping don't have to happen on the server. It is actually better to do the final sealing on your laptop, because (1) the private signing key then never sits on the public server, and (2) your laptop has open internet, so the trusted-timestamp (TSA) call just works — no PythonAnywhere whitelisting or paid tier needed. The server's job is only to assemble the content.

  1. Download the content. On the Cycles page, click Sign on laptop. This downloads Audit_<AY>_<CODE>_<time>_UNSIGNED.pdf.
  2. Seal it on the laptop. In the app/ folder run: 
    python sign_audit.py Audit_..._UNSIGNED.pdf
    It signs with the college certificate (created on this machine the first time) and, if FEEDBACK_TSA_URL is set in app/.env, adds a trusted timestamp. It writes Audit_..._signed.pdf and prints the SHA-256 fingerprint.
    Options: --tsa https://freetsa.org/tsr to set the TSA for this run, or --no-tsa to sign without a timestamp.
  3. Store it. Put Audit_..._signed.pdf in the Dean's / Vice-Dean's Drive — that is the official audit reference copy.
Keep the file app/data/afs_signing_key.pem (created on the machine that signs) private and backed up — it is the college's signing key. If you sign on the laptop, this key should live only on the laptop, never on the server.

The Audit report button still signs on the server for convenience (handy when you don't need a timestamp); on the free tier it simply won't add a timestamp. For the official, timestamped copy, prefer Sign on laptop.

9 · Upgrading the LIVE server to v2.1 — do this ONCE

One-time only. Everything in this box is part of setting up / upgrading the web app — you do it once, when you move the server to v2.1. It is not repeated for each feedback round. Running a normal cycle afterwards never touches these steps (see “10 · Running a cycle” just below for the repeatable routine).
  1. Pull the new code onto the server — your usual git fetch → reset → reload.
  2. Add the two test inboxes to the WSGI file. There is no .env on the server — your environment variables live in the WSGI file, the same place as your Gmail keys (see Hosting, Step 6). Add these two lines there: 
    os.environ["FEEDBACK_TEST_EMAIL"]          = "aishwarya.bramma@gmail.com"
os.environ["FEEDBACK_FACULTY_ALIAS_EMAIL"] = "aishwarya@sret.edu.in"
    The up-to-date WSGI file (with these lines already in it) is in your project folder as WSGI File for Python anywhere Feedback System.txt — copy it over if you prefer.
  3. Install the signing library in the feedback virtualenv: 
    pip install pyhanko
  4. Run the database migrations (idempotent — safe to re-run), in ~/feedback-system: 
    python migrate_defaults_7_5_0.py        # POOR < 7.5, min responses 0
python migrate_v2_module6_testlevels.py # the test-level column
python migrate_admin_flag.py            # the is_admin flag
python seed_admins.py                   # grant admin access to the two accounts
  5. Reload the web app (Web tab → Reload).
  6. Each admin sets their password via /admin/forgot.
Databases never travel through GitHub, so the migration scripts must run on the server (or the updated master.db re-uploaded). Running them only on your laptop updates only your laptop.
You do not set FEEDBACK_TSA_URL on the server — the audit report is signed & timestamped on your laptop (section 8a), where the network is open.

10 · Running a cycle — the routine (EVERY round)

Once the app is set up (section 9, done once), this is the repeatable flow for each feedback round. None of the one-time setup above is repeated. Creating and running a new cycle is all done from the web pages:

  1. Create the cycle (Cycles → Create) — it starts safely at Level 1.
  2. Upload the roster, allocation and enrollment, and pass the Readiness check.
  3. Test up the levels: open at Level 1 (all mail goes to your test inboxes) and check; then Set level → 2 (real staff, test students), then → 3 (all real, watermarked), checking each time.
  4. Purge → Production: type PURGE <CODE>. This wipes the test feedback but keeps the roster, offerings and faculty, and flips the cycle to the real Level-0 run. Open it and invite the real students.
  5. Collect feedback, then Close the cycle; on Results & send classify (POOR below 7.5) and email the teachers their results.
  6. Teachers file ATRs; HOD → Vice-Dean → Dean endorse (the Dean/Vice-Dean can use Endorse all). When the Dean closes the last one the cycle turns RECORDED.
  7. Audit report → Sign on laptop → store the signed PDF in the Dean's / Vice-Dean's Drive.
  8. Archive the cycle — it then drops out of every dropdown, keeping the pages clean for the next round.

11 · Starting over — wipe ALL cycles (housekeeping, rare)

If you want a completely clean slate — for example after a round of testing, or to clear an old year and begin fresh — this removes every cycle and everything tied to a cycle in one step, while keeping the things that live across cycles.

RemovedKept
All cycles, the allocation (offerings), the student roster (and roster ranges), enrollment, the GOOD/POOR bands, readiness dismissals, every per-cycle database (data/cycle_*.db), and the archived cycle files. The Faculty Master, all leader/admin logins, departments, programmes, the feedback templates/scales/questions, the academic-year label, and the IAM tables.
This is destructive and cannot be undone. It only runs when you pass --yes. Always --dry-run first to see exactly what it will remove. Because databases never travel through git, run it in both places — your laptop and the server.
Not the same as “Purge → Production”. Purge (section 2) clears ONE cycle's test feedback but keeps its roster and allocation, to promote that same cycle to the real run. This reset wipes everything, including the roster and allocation, so you re-upload from scratch.
  1. Preview (touches nothing), in the app/ / ~/feedback-system folder: 
    python reset_all_cycles.py --dry-run
  2. Do it: 
    python reset_all_cycles.py --yes
    Optional extras on the same line: --clear-activity also wipes the audit/activity log; --unlock-templates unlocks templates that locked during testing so you can edit questions again. A fully clean slate is python reset_all_cycles.py --yes --clear-activity --unlock-templates.
  3. On the server, do the same after pulling the code, then reload: 
    cd ~/feedback-system
git fetch origin && git reset --hard origin/main
python reset_all_cycles.py --yes
touch /var/www/SRETfeedback_pythonanywhere_com_wsgi.py
If a few old data/cycle_*.db or archive/ files can't be auto-deleted (a rare file-permission case), just delete them by hand — they are harmless orphans that no cycle refers to. After the reset, create ONE fresh cycle and upload the real roster + allocation.

ADMIN  Putting the code on GitHub — safely

GitHub is where the code of the app lives online: it is your backup, and it is what PythonAnywhere pulls from when you deploy (next section). The single most important rule:

The repository holds CODE ONLY. Never put secrets (your Gmail keys) or real data (databases, student rosters, faculty contacts) on GitHub. A file called .gitignore inside the app/ folder lists everything git must skip. It is already set up for you.

What is deliberately kept OUT (and why)

Not pushedWhy
.envHolds your Gmail client secret and refresh token — treat like a password.
data/ (all .db files)The live databases — real student responses and faculty/student identities.
data/faculty_roster.tsvFaculty names, phone numbers, emails.
uploads_tmp/, archive/, outbox/Uploaded rosters, archived cycles, generated emails — all personal data.
__pycache__/Python build junk — regenerated automatically.

Everything else — the Python files, the HTML templates, the .md guides — is pushed. So a fresh copy of the repo has the full working app but none of your data or secrets.

First-time push (run inside the app/ folder)

Use Git Bash on Windows. Each line is one step; run them in order.

git init
git add .
git ls-files | grep -E "\.db|\.env|\.tsv|xlsx|__pycache__"   # SAFETY CHECK
# ^ this must print NOTHING. If it lists any file, stop — do not commit.
git commit -m "SRET Feedback System — code only"
git branch -M main
git remote add origin https://github.com/<you>/<repo>.git
git push -u origin main
The git ls-files | grep … line is your seat-belt: it lists any database, secret, spreadsheet or cache that slipped into the repo. If it prints nothing, you are safe to commit.

If GitHub blocks the push (“secret detected”)

GitHub scans your history, not just the current files, so deleting a secret file is not enough — the secret is still in an earlier commit. Do not click GitHub’s “allow secret” link (that would publish it). Instead rebuild the history clean:

rm -rf .git            # PowerShell: Remove-Item -Recurse -Force .git
git init
git add .
git ls-files | grep -E "\.db|\.env|\.tsv|xlsx"   # must be empty
git commit -m "SRET Feedback System — code only"
git branch -M main
git remote add origin https://github.com/<you>/<repo>.git
git push -u origin main --force

Because .gitignore is now in place, the secret and data files are not re-added, and the brand-new history contains no trace of them.

If a Gmail secret was ever pushed, rotate it afterwards: Google Cloud Console → APIs & Services → Credentials → your OAuth client → Reset secret, then paste the new value into app/.env. Your refresh token keeps working (it is tied to the client ID, not the secret value).

ADMIN  Updating the server after a change

When a change is made to the code and tested on your laptop, the live PythonAnywhere site does NOT update by itself. You push the change to GitHub, pull it on the server, and reload. Always do it this way — pushing the whole project through git — rather than copying single files by hand, which quietly breaks a page when one line is missed.

Golden rule: code changes travel through git (push from laptop → pull on server → reload). Your WSGI file (where your secrets live, in /var/www/, outside the repo) and your databases are never touched by this — git ignores the databases and never sees the WSGI file.

Step 1 — Push from your laptop (in the app folder)

git add .
git commit -m "describe what changed"
git push

Step 2 — Pull onto the server (PythonAnywhere Bash console)

cd ~/feedback-system
git fetch origin
git reset --hard origin/main

git reset --hard origin/main forces the server's code to become an exact copy of what you just pushed — so every changed file lands together, correctly. It does NOT touch your WSGI file (your secrets live there, in /var/www/, outside the repo) or your data/ databases (git ignores those), so your secrets and data are safe.

Step 3 — Reload the web app

touch /var/www/SRETfeedback_pythonanywhere_com_wsgi.py

…or just click the green Reload button on the Web tab. Then refresh the page you changed.

Data-only changes are different. If you changed data rather than code — for example a maintenance script that edits master.db, or a fixed roster — git will not carry it (databases are git-ignored). For those, either run the same script on the server (python <script>.py in the Bash console) or re-upload the database via the Files tab.

If something breaks after a change

  1. Open the error log: Web tab → Log files → Error log (SRETfeedback.pythonanywhere.com.error.log), or in a Bash console: 
    tail -n 40 /var/log/SRETfeedback.pythonanywhere.com.error.log
    The newest error is at the bottom; the last line names the file, line number and problem.
  2. Fix it on your laptop, test, then repeat Steps 1–3. Avoid hand-editing on the server — it drifts out of sync with GitHub and causes exactly the kind of one-line breakages that are hard to find.

A word on privacy — for everyone

Student answers are anonymous by design. The system stores who participated (so reminders can be sent) completely separately from the answers themselves, in different files that share no link — so an answer can never be traced back to a student. The activity log records the people who run the system (Admin, Leaders, Faculty), and never records a student's submission. Reports show scores and averages, never individual responses.
